The Transformer, Number by Number  ·  Part 6

How the Decoder Writes

By Hao Ma  ·  haoma7.github.io

Part 5 showed how the encoder turns an input sentence into vectors. Those vectors carry information about the sentence, but they are not yet a translation. How does the decoder use that information to generate a translation, one token at a time?

Our example. We start with the English sentence I love LLMs and use J’aime les grands modèles (“I love large models”) as a simplified French translation. We will follow how an encoder–decoder model chooses each French token and decides when to stop.

For this illustration, treat each displayed word—including J’aime—as one token: three in the English sentence and four in the French translation. Real tokenizers may split these words differently. The French choices are illustrative, so we can concentrate on the generation process.

This is inference: we use a model that has already been trained, keeping its weights fixed. Here, we use it to generate a translation one token at a time. We call this repeated process the generation loop.

We will first identify the decoder’s inputs, then examine its output vectors and how one vector becomes a token choice. Finally, we will connect the runs to generate the complete translation.

What you need. Vectors, dot products, softmax, embedding lookup, and the encoder block from Part 5.

6.1What information does the decoder use?

Imagine that the model has already generated J’aime les and is now choosing what comes next. Each decoder run is used to choose one next token, so this is run 3.

The decoder receives two inputs:

  • The target prefix: <start> J’aime les. This is the French translation generated so far, preceded by <start>, a special token that marks the beginning of generation.
  • Source memory: the three vectors the encoder has computed for I love LLMs. They carry information about the English sentence.

Figure 1 shows the target prefix entering from the bottom and source memory entering from the side. These are the two “doors” into the decoder.

6.1.1The bottom input: the target prefix

Each token in <start> J’aime les is represented by an embedding vector, with positional information to indicate its place in the sequence. These three tokens therefore give three input rows. Self-attention lets the decoder use information from this prefix when choosing the next French token.

As more French tokens are generated, they join the target prefix. Section 6.4 will trace that process across all the runs.

6.1.2The side input: source memory

The encoder processes I love LLMs once, before generation begins. The resulting source memory stays fixed throughout this translation. Cross-attention lets the decoder use information from these vectors when choosing each French token.

Both inputs happen to have three rows in Figure 1. Their lengths do not have to match: the target prefix grows, while source memory still contains the same three vectors.

6.1.3How the source sentence changes the result

To see why source memory matters, go back to the beginning, before any French token has been generated.

Consider translating I love LLMs and LLMs love me. Both tasks begin with the same target prefix, <start>, and use the same model. Why can their first French tokens be different?

The English sentences produce different source memory. The decoder therefore has different source information to use when choosing the first French token, even though the starting target prefix is the same.

Key takeawayThe decoder uses two inputs together: the target prefix, which grows as French tokens are generated, and source memory, which carries information about the English sentence and stays fixed throughout its translation.

Try it (1 minute): Begin a new translation with LLMs love me instead of I love LLMs. Before generating the first French token, which of the decoder’s two inputs changes, and which stays the same?

Check your answer

Source memory changes because the encoder processes a different English sentence. The starting target prefix is still the single token <start>.

We now know what goes into the decoder. What vectors come out, and which one is used to choose the next token?

6.2What does one decoder run produce?

On run 3 in Figure 1, we feed <start> J’aime les into the decoder: the start token followed by the French tokens generated so far. The decoder updates the vectors for these three tokens using information from the target prefix and source memory. When its calculations finish, we have three output vectors: one for <start>, one for J’aime, and one for les.

These output vectors are called the decoder’s final hidden states. Here, “final” means that the decoder has finished its calculations for the current run. There is one such vector for each input token.

The next step is to use one of these vectors to choose the next French token. Which vector should we use?

6.2.1Why use the vector for the last input token?

We already have <start> J’aime les. Our next task is to choose the token that comes after les.

During training, the model learns to use the output vector at each position to predict the token immediately after that position. For this run, we therefore use the output vector for les.

We send this vector to the output head, which computes a score for each possible next token. This vector corresponds to the position of les, but it already incorporates information from earlier French tokens through self-attention and from the English sentence through cross-attention.

Arrange the output vectors as a matrix in the same order as the input tokens, with one vector per row. The vector for les is in the last row, highlighted in Figure 3.

Key takeawayProcessing the full prefix produces one final hidden-state vector per input token. We use the vector for the last input token to choose the next token. This vector already incorporates information from the preceding tokens and the English source sentence.

We now know which vector to use. But a vector contains numbers, not a token choice. How does the output head turn those numbers into scores for the possible next tokens?

6.3How does one vector become a token choice?

We already have <start> J’aime les and want to choose the token after les. Section 6.2 showed which vector to use: the decoder’s final hidden-state vector for les. We will call this vector \(\mathbf{h}\).

For this worked example, suppose the decoder has produced:

\[\mathbf{h}=(1,\ 2,\ -1,\ 0.5).\]

The decoder’s output vector is the output head’s input. The four numbers in \(\mathbf{h}\) are the starting point for our calculation. The vector and output weights below are illustrative values chosen for hand calculation.

To choose the next token, the model first assigns a score to each token in its vocabulary. The output head computes these scores from \(\mathbf{h}\). We will calculate the scores, turn them into probabilities, and then select a token.

6.3.1Score each vocabulary token

The vocabulary is the set of tokens the model can choose from. Our small example uses six entries: <start>, J’aime, les, grands, modèles, and <end>. We will compute a score for every entry.

<end> is a special token that signals the end of the translation; selecting it tells the generation program to stop.

Each score indicates how strongly the model favours a candidate as the next token. A higher score means a stronger preference.

For this prediction, we use the decoder’s final vector \(\mathbf{h}\) for les. The output head has a learned weight vector for each candidate token. On this run, all six candidates are scored using the same \(\mathbf{h}\), but each candidate has its own output weights. On the next run, the decoder computes a new \(\mathbf{h}\); the output weights stay fixed.

Each output-weight vector contains four numbers to match the four components of \(\mathbf{h}\). To score a candidate, take the dot product of \(\mathbf{h}\) and that candidate’s weights: multiply matching components, then add the products.

For grands, use the output weights \((1,1,0,0)\). Call its score \(z_{\text{grands}}\). The calculation is:

\[ z_{\text{grands}}=(1)(1)+(2)(1)+(-1)(0)+(0.5)(0)=3. \]

The table applies the same calculation to all six candidates, always using the same input vector \(\mathbf{h}=(1,2,-1,0.5)\):

These six scores are called logits. They are the output of the output head: one number for each vocabulary token. They can be negative and do not have to sum to one. The largest score here belongs to grands.

Compute all six scores with one matrix multiplication

Place each candidate’s output-weight vector in a column of a matrix called \(\mathbf{W}_{\text{out}}\). Keep the same candidate order as the table:

\[ \mathbf{W}_{\text{out}}= \begin{bmatrix} 0 & 0 & 0 & 1 & 1 & 0\\ -1 & 0 & 0 & 1 & 0 & 0\\ 0 & 1 & 0 & 0 & 0 & 1\\ 0 & 0 & 1 & 0 & 0 & 1 \end{bmatrix}. \]

Collect the six scores into a vector called \(\mathbf{z}\), keeping the vocabulary order shown in the table. Each entry of \(\mathbf{z}\) corresponds to one candidate token. Multiplying \(\mathbf{h}\) by the weight matrix computes all six scores at once:

\[ \mathbf{z}=\mathbf{h}\mathbf{W}_{\text{out}} =(1,2,-1,0.5)\mathbf{W}_{\text{out}} =(-2,\ -1,\ 0.5,\ 3,\ 1,\ -0.5). \tag{6-1} \]

The dimensions show what changes: a 1 × 4 input vector multiplied by a 4 × 6 weight matrix gives 1 × 6 logits. The four entries of \(\mathbf{h}\) describe the decoder’s hidden state; the six entries of \(\mathbf{z}\) score the six candidate tokens.

6.3.2Turn logits into probabilities

Softmax takes all six logits together and converts them into probabilities. First, exponentiate each score. Then divide each result by the sum of all six exponentials.

For candidate token \(j\), let \(z_j\) be its logit and \(p_j\) its probability. With \(V=6\) vocabulary entries:

\[p_j=\frac{e^{z_j}}{\sum_{k=1}^{V}e^{z_k}}.\]

Every candidate uses the same denominator:

\[ \begin{aligned} S &=e^{-2}+e^{-1}+e^{0.5}+e^3+e^1+e^{-0.5}\\ &\approx25.562285. \end{aligned} \]

For grands, divide the exponential of its score, 3, by this total:

\[p_{\text{grands}}=\frac{e^3}{S}\approx\frac{20.085537}{25.562285}\approx0.7857.\]

Repeating that division for each candidate gives:

Choose the next token

Softmax gives us six probabilities. To select a token, this example uses greedy selection: choose the token with the largest probability. That token is grands, with probability about 0.7857.

Softmax preserves the order of the scores, so greedy selection could also choose the largest logit directly. Calculating the probabilities lets us see how the score for grands compares with all the other candidates.

We have now selected grands. Append it to the existing tokens, giving <start> J’aime les grands as the input for the next run.

Optional: computing softmax without very large exponentials

Subtract the largest logit \(m\) before exponentiating: \(p_j=e^{z_j-m}/\sum_k e^{z_k-m}\). The shared factor cancels, so the probabilities are unchanged. Here \(m=3\); the shifted logits are \((-5,-4,-2.5,0,-2,-3.5)\). This form helps avoid numerical overflow.

Extra practice: use the same weights on the next run

The next input is <start> J’aime les grands. Suppose the decoder’s final vector for grands is now \(\mathbf{h}'=(2,-1,0,0)\). This is another illustrative vector. Keep the output weights fixed. Calculate all six logits and identify the greedy choice.

Check the calculation

In the same vocabulary order, the logits are \((1,0,0,1,2,0)\). The largest score is 2 for modèles, so greedy selection chooses modèles. Softmax would give approximately \((0.1718,0.0632,0.0632,0.1718,0.4669,0.0632)\); it preserves that ordering.

The decoder supplies a new hidden-state vector on each run, while the learned output weights stay fixed during generation.

Optional: weight tying saves parameters

Weight tying uses the same learned parameters for the decoder’s input embeddings and output weights. In our six-token example, separate matrices need 24 + 24 = 48 parameters; sharing needs only 24. These counts cover those two matrices, not the whole model.

For example, with weight tying, the output-weight vector \((1,1,0,0)\) for grands also serves as its input embedding. At input, the token ID selects this vector; at output, its dot product with \(\mathbf{h}\) scores grands. The decoder still computes \(\mathbf{h}\) from the current context.

If the embedding table is \(\mathbf{E}\), with one token per row, sharing gives \(\mathbf{W}_{\text{out}}=\mathbf{E}^{\top}\), because the output matrix stores candidate weights in columns. Weight tying is optional; the scoring and token-selection steps work with separately learned weights too.

Optional: an output bias

The output head may also add a learned bias \(\mathbf{b}\), giving \(\mathbf{z}=\mathbf{h}\mathbf{W}_{\text{out}}+\mathbf{b}\). Our worked calculation omits this bias.

Key takeawayThe vector for les is the output head’s input. The output head produces one logit per vocabulary token. Softmax turns the logits into probabilities, and greedy selection chooses grands in this example.

6.4How does the model generate a complete translation?

Section 6.3 showed how to choose one token. To generate a complete translation, we add the selected token to the target prefix and run the decoder again.

The encoder processes the English sentence once. The same source memory is used on every decoder run; the target prefix changes as new French tokens are selected. The model weights stay fixed throughout generation.

6.4.1Start, select, append, and repeat

Before the first run, no French tokens have been generated. Begin with the single token <start>, which lets the decoder compute a vector for choosing the first French token.

  1. Read the prefix. Take <start> and all French tokens generated so far as this run’s target input.
  2. Compute the vectors. Represent the input tokens with embeddings and positional information, then run the decoder with source memory. This produces one final hidden-state vector per input token.
  3. Select a token. Apply the output head to the vector for the last input token. Greedy selection chooses the token with the largest score; as Section 6.3 showed, softmax gives the same ranking.
  4. Append or stop. The special token <end> tells the generation code to stop. Otherwise, append the selected token to the target prefix and begin the next run.

For example, run 1 takes <start> as its input and selects J’aime. Append that token: run 2 now takes <start> J’aime as its input and selects the next token.

Figure 5 lets you follow the complete translation. Each run is shown in the same four steps: read the prefix, compute the vectors, select a token, and append or stop. The demonstration processes the whole prefix again on each run.

The completed example has three English source tokens and four French translation tokens. Their lengths can differ because each decoder run selects one new token, and the model can continue until it selects <end>. The source memory stays at three vectors throughout.

6.4.2Stop when the model selects <end>

The output vocabulary includes the special token <end>. The output head scores it along with the other candidate tokens. When token selection chooses it, the generation code stops.

On run 5, the input is <start> J’aime les grands modèles. The final hidden-state vector for modèles goes to the output head, and token selection chooses <end>. The program then stops: there is no run 6. The end marker is not displayed, so the translation contains the four French tokens.

During training, completed target sequences include an end token. The model learns to predict it after the final translation token. During generation, the program stops when that token is selected. A practical implementation also sets a maximum generation length, so generation can stop at that limit even if no end token is selected.

Looking ahead to Part 10: selection rules and caching

Other ways to choose a token. Greedy selection is the rule used in this example. Sampling and beam search use the scores differently; Part 10 develops these choices. Softmax supplies probabilities; the selection rule determines what happens next.

Avoiding repeated work. This demonstration processes the whole prefix on every run. A KV cache saves part of the earlier computation so later runs can process only the new token while still using information from earlier tokens. Part 10 explains what is saved and how it is reused.

Key takeawayBegin with <start>. Use the decoder’s final vector for the last input token to select the next token. If it is <end>, stop; otherwise, append it to the prefix for the next run. The prefix grows, while source memory and model weights stay fixed. A generation-length limit provides another stopping condition.

6.5What changes in a decoder-only model?

So far, we have used an encoder–decoder model: the encoder processes the English sentence, and the decoder generates the French translation. We now consider a different architecture, a decoder-only language model, to see how the same token-by-token generation loop works there.

For the same translation task, the initial input could be:

Translate into French: I love LLMs. French:

This initial text is the prompt. It contains the translation instruction and the English source sentence; French: cues the model to continue with the translation. As French tokens are generated, they are appended after the prompt.

The prompt is tokenized before it enters the model. The displayed text therefore represents a sequence of input tokens; its exact token boundaries depend on the tokenizer. Run 1 already has all of these prompt tokens as input, before any French token has been generated.

Compare how the two models receive the English source information:

ModelWhere the source sentence enters
Encoder–decoderThe encoder processes I love LLMs. Its output becomes source memory, read by the decoder through cross-attention.
Decoder-onlyThe source is part of the prompt shown above. The prompt and the French tokens generated so far enter together as one sequence, processed through self-attention.

The decoder-only model has no separate encoder and no cross-attention to encoder outputs. Like the decoder in our encoder–decoder model, it uses causal self-attention: each position can use information from that position and earlier positions. The last input position can therefore use information from the entire input so far: the prompt and any French tokens already generated. A suitably trained model can use that information to translate.

As in the earlier walkthrough, we describe generation by processing the complete input sequence on each run, without a KV cache. The model produces one final hidden-state row per input token. On run 1, that means one row for each prompt token; the last row belongs to the prompt’s last token and is used to choose the first French token.

Now follow the first two runs. We keep the simplified French token units used earlier and suppose this model selects J’aime, then les:

1Translate into French: I love LLMs. French:The final hidden-state vector for the prompt’s last token.J’aime
2Translate into French: I love LLMs. French: J’aimeThe final hidden-state vector for J’aime.les

Run 1 selects J’aime, which is appended for run 2. Run 2 computes its hidden-state vector and uses it to select les, which is appended for run 3. A selected token gets its own hidden-state row when it is processed on the next run. As in Section 6.3, the output head converts the last row into vocabulary scores, and token selection chooses the next token.

Continue appending selected tokens and running the model until a stopping condition is met, such as selecting an end token or reaching the generation-length limit. The displayed translation contains the generated French tokens; the prompt remains part of the model’s input.

Key takeawayAn encoder–decoder model receives source information through separate source memory. A decoder-only model receives it within the prompt. In both, the final vector for the last input token goes to the output head. Select the next token; if generation continues, append it for the next run.

The generation loop follows the four stages in Figure 5. Read the prefix: take the current input tokens. Compute the vectors: run the decoder to obtain their final hidden states. Select a token: use the output head to score candidates from the last hidden-state vector, then apply the selection rule. Append or stop: stop at <end>; otherwise, append the selected token for the next run. A generation-length limit can also stop the loop.
